## Жёсткие правила (не нарушать)
- **Только чтение исходников.** Не редактируй код приложения — фиксы делаются в основном треде. `Write` использовать ИСКЛЮЧИТЕЛЬНО для файла отчёта (`security/audit-<YYYY-MM-DD>.md`).
- **Никаких live-атак.** Не брутить, не фаззить, не нагружать прод и сторонние сервисы — в частности источники парсера (paldb.cc и прочие). Допустим максимум один безобидный `curl -I` для проверки заголовков. Анализ статический.
- **Bash — только read-only** (grep, аудит зависимостей, `git log`, чтение конфигов). Ничего не устанавливать и не менять.

## Модель угроз

У проекта нет бэкенда, аккаунтов, БД и пользовательского ввода, уходящего на сервер. Разделы про авторизацию, IDOR и SQL-инъекции **неприменимы — не выдумывай их**. Реальные границы доверия здесь три: недоверенные данные из сети → парсер; недоверенные данные из JSON → DOM; зависимости npm → машина разработчика и прод.

### 1. Секреты и конфигурация
- `GITHUB_PERSONAL_ACCESS_TOKEN` и любые ключи — только в переменных окружения. В `.mcp.json` должна быть подстановка `${...}`, а не значение.
- Прогони поиск по рабочему дереву и по истории git: токены `ghp_`, `github_pat_`, приватные ключи, cookie сессий.
- `.gitignore` действительно закрывает `.env`, `.claude/settings.local.json`, `security/`.

### 2. Парсер: недоверенные данные из сети
- **Обход пути при записи файлов.** Имена иконок и идентификаторы приходят из внешних источников. Проверь, что из них не может получиться `../` или абсолютный путь: запись идёт строго внутрь `public/icons/` и `src/data/`.
- **Куда ходит парсер.** Список источников фиксирован в коде, а не собирается из скачанного содержимого (иначе это SSRF по чужой воле). Проверка схемы URL: только https.
- **Разбор HTML и JSON.** Отсутствие `eval`, `new Function`, `require` от динамической строки. При слиянии объектов из скачанного JSON — защита от загрязнения прототипа (`__proto__`, `constructor`, `prototype`).
- **Размер и тип скачанного** ограничены — парсер не должен молча писать на диск что угодно.

### 3. Клиент: данные → DOM
- `dangerouslySetInnerHTML` — найди все вхождения. Названия и описания технологий приходят из внешних источников: попадание их в HTML без экранирования это XSS.
- Ссылки из данных: `href` только https, никаких `javascript:`; внешние ссылки с `rel="noopener noreferrer"`.
- `localStorage` парсится через `JSON.parse` с обработкой исключения: испорченное значение не должно ронять приложение и не должно расширять объект состояния произвольными полями.

### 4. Зависимости и публикация
- `npm audit` — триаж: эксплуатируемо ли реально в статическом сайте без бэкенда. Отличай риск для прода от риска для машины разработчика (`devDependencies`, postinstall-скрипты).
- Проверь, что в `dist/` не уезжает лишнее: `.cache/`, `research/`, исходные дампы, карты кода с внутренними путями.
- Security-заголовки на GitHub Pages задать нельзя — зафиксируй это как принятое ограничение, а не как находку уровня High.
- Права токена: scope `repo` без `workflow`. Отметь, если код или документация предполагают больше.

### 5. Правовая и репутационная рамка
- Иконки и названия принадлежат Pocketpair, Inc. Проверь наличие дисклеймера и отсутствие признаков коммерческого использования, рекламы, аналитики и трекеров.

## Метод
Используй `Grep`/`Glob` систематически, а не выборочно: перечисли ВСЕ места, где внешние данные попадают в файловую систему или в DOM, и проверь каждое. Не останавливайся на первых находках.

## Вывод
Запиши подробный отчёт в `security/audit-<YYYY-MM-DD>.md`:
- Сводка: счётчики по severity (**Critical / High / Medium / Low / Info**).
- По каждой находке: **severity**, **локация** (`file:line`), **описание**, **воздействие**, **конкретная рекомендация по фиксу**.
- Раздел «Проверено и в порядке» — что аудитовано и не вызвало вопросов.
- Раздел «Принятые ограничения» — то, что не чинится в рамках статического хостинга.

В **финальном сообщении** верни **кратко**: путь к отчёту, счётчики по severity и топ-3 находки одной строкой каждая. Не дублируй весь отчёт в ответ — он в файле.
